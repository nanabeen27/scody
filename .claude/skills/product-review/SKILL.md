# /product-review

`product-manager`(흐름·빠진 메커니즘) + `ux-auditor`(위계·클릭 가능성·문구·상태·모바일)로 검토하고, 명백한 문제는 `product-fixer`로 고친 뒤 검증한다.

인자가 있으면 **그 범위만** 본다.

```
/product-review 학생 홈
/product-review 과제 풀이 화면
/product-review 학원 과제 생성부터 학생 제출까지
```

인자가 없으면 범위를 먼저 정한다. 최근 작업한 화면이 있으면 그것을 제안하고, 아니면 어느 화면·흐름을 볼지 사용자에게 묻는다. **전체 앱을 한 번에 훑지 않는다** — 검토가 얕아지고 고칠 것도 흐려진다.

## 순서

### 1. 범위 확정

인자를 라우트와 파일로 옮긴다. 예: "학생 홈" → `app/student/index.tsx` + 거기서 쓰는 `src/features/learning.ts`·`src/components/*`. 흐름이면 관련 화면을 순서대로 나열한다(예: 배정 → 학생 홈 → 풀이 → 결과 → 학원 제출 현황).

찾은 범위를 한 줄로 사용자에게 알리고 진행한다.

### 2. 두 관점 병렬 검토

`product-manager`와 `ux-auditor`를 **한 메시지에서 동시에** 띄운다(서로 독립적이다). 각 에이전트에게 범위와 해당 파일 경로를 함께 넘긴다.

둘 다 읽기 전용이라 화면을 실행해 보지 못한다. 코드만으로 확정할 수 없는 항목은 각 보고의 `실제 화면 확인이 필요한 것`에 남으니, **그 목록은 이 스킬이 5단계에서 직접 확인한다.**

### 3. 합치기

두 보고를 하나의 실행 목록으로 만든다.

- 같은 문제를 다르게 말한 항목은 **하나로 묶는다**(코드 근거가 같은 줄을 가리키면 같은 문제다).
- 등급이 다르면 **높은 쪽**을 따르되, 사용자 영향으로 다시 판단해 조정한 이유를 적는다.
- `docs/SCODY_MASTER_PLAN.md` 6절에 이미 있는 항목은 새 발견에서 빼고 ID로 참조한다.
- 확정 정책(2·4·7절)과 부딪히는 항목은 **고치는 목록에 넣지 않고** `결정 대기` 후보로 분리한다.

### 4. 고치기

**Critical과 High 중에서 명백하고 안전한 것만** `product-fixer`에게 넘긴다. 넘길 때 문제·근거 경로·기대 결과를 함께 준다.

다음은 넘기지 않고 사용자 판단으로 남긴다.

- 확정 정책·정보 구조를 바꿔야 하는 것
- 백엔드·결제·실제 인증이 필요한 것(프로토타입 범위 밖)
- 여러 화면을 동시에 다시 설계해야 하는 것
- 고치는 방법이 두 가지 이상이고 어느 쪽인지 사용자가 정해야 하는 것

한 번에 여러 항목을 넘길 때는 서로 같은 파일을 건드리는지 확인한다. 겹치면 순서대로 하나씩 보낸다.

### 5. 검증

이 프로젝트에는 `/verify`가 없다. 프로젝트 절차를 쓴다.

| 목적 | 명령 |
|---|---|
| 타입 검사 | `npm run typecheck` |
| 린트 | `npm run lint` (오류 0) |
| 단위·통합 | `npm test` |
| 사용자 흐름 | `npx playwright test` (desktop·tablet·mobile) |
| 화면 | `npm run web` → 1280 · 820 · 390 + 다크 |

`product-fixer`가 이미 돌렸어도 **마지막에 전체 E2E를 한 번 더** 돌린다(여러 항목을 고친 뒤의 상호작용을 잡기 위해).

화면 확인은 두 가지를 함께 한다.

1. 고친 화면이 세 뷰포트와 다크에서 의도대로 보이는지
2. 두 검토 에이전트가 남긴 **`실제 화면 확인이 필요한 것`** 목록 — 코드만으로 판단할 수 없던 항목(실제 줄바꿈, 대비, 스크롤, 빈·오류 상태의 실제 모습)

로그인은 휴대폰 번호 + 인증번호 `000000`이다. 계정 성격이 달라 무엇을 보려는지에 따라 고른다.

| 계정 | 번호 | 성격 |
|---|---|---|
| 김서준 | `010-1000-0001` | 개인 학습만 |
| 박도윤 | `010-1000-0003` | 학원 이용권만(미제출 과제 있음) |
| 정예린 | `010-1000-0004` | 개인 + 학원 |
| 이민지 | `010-2000-0001` | 학부모 |
| 한빛 원장 | `010-3000-0001` | 학원 |

세션은 메모리에만 있어 `page.goto`로 새로 진입하면 로그아웃된다. 화면 이동은 앱 안에서 한다. 임시 스크립트·이미지는 `/tmp`에 두고, 남길 근거만 `docs/evidence/`에 저장한다.

### 6. 실패하면 다시

검증이 깨지면 원인을 찾아 고치고 다시 돌린다. 테스트를 지우거나 skip해서 통과시키지 않는다. 문구·흐름을 의도적으로 바꿔 테스트를 고쳤다면 무엇을 왜 바꿨는지 보고에 남긴다.

### 7. 기록

`docs/archive/SCODY_WORKLOG_2026-07.md`에 검토·수정·검증 결과를 적는다. 새 판단이 생겼으면 마스터 플랜 7절에 `D-0xx`, 남은 문제는 6절에 ID와 완료 조건으로 남긴다.

## 평가 기준

두 에이전트와 최종 판단이 공통으로 쓰는 기준이다.

1. 사용자가 **3초 안에 다음 행동을 이해**하는가
2. 핵심 행동이 **시각적으로 가장 강하게** 드러나는가
3. 기능 사이의 관계와 **상태 전이**가 자연스러운가(들어갈 길·돌아올 길·끝난 뒤 다음 행동)
4. **빈 상태 · 진행 · 완료 · 실패 · 재시도**가 정의되어 있는가
5. 클릭 가능한 요소가 **명백하게 클릭 가능해** 보이는가
6. 서비스의 **용어와 문구가 일관**적인가(존댓말 `-어요`, 한 문장에 한 가지)
7. **임시 데이터·하드코딩에 의존**하지 않는가(fixture를 실제처럼 보여주지 않는가)
8. **실제 서비스 운영이 가능한 구조**인가(상태·타입·권한 경계가 함께 있는가)
9. **개인 학습과 학원 과제**의 출처·권한이 섞이지 않는가

## 보고 형식

```
## 검토 범위
## 발견한 핵심 문제        — 등급별로, 코드 근거와 함께
## 수정한 항목             — 무엇을 어떻게, 변경 파일
## 수정하지 않은 항목과 이유 — 정책 충돌 / 범위 밖 / 사용자 판단 필요 / 재현 안 됨
## 검증 결과               — typecheck · lint · test(N) · e2e(N, 3뷰포트) · 화면 확인 뷰포트·테마
## 다음 개선 후보           — 우선순위 순
```

문제가 없으면 없다고 쓴다. 등급을 채우기 위해 항목을 만들지 않는다.
