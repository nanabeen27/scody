# SCody 학습 기록·성취 시스템 구현 명세

이 문서는 요청받은 요구사항을 축약 없이 구현 명세 형태로 기록한 것이다. 아직 구현되지 않았다. 설계 결정과 구현 결과는 별도로 이 문서에 추가한다.

상태: `구현 완료 · 검증 완료`(2026-08-19, D-179). 채택한 설계와 구현 결과는 이 문서 13절부터.

---

## 0. 목표

SCody에 학생의 실제 학습 활동이 장기간 '기록'으로 쌓이고, 학생에게는 강한 성취감과 계속 공부하고 싶은 욕구를 주며, 학부모에게는 자녀가 실제로 얼마나 꾸준히 공부하고 있는지를 가시적으로 보여 주는 본격적인 **학습 기록·성취 시스템**을 기획하고 구현한다.

목표는 '통계 페이지 하나 추가'가 아니다.

**학생이 SCody를 오래 사용할수록 떠나기 아까울 정도로 자신의 학습 기록이 쌓이고, 공부한 하루하루가 눈에 보이는 자산이 되는 시스템을 만든다.**

## 1. 사전 조사 요구사항

단순히 Duolingo의 streak를 복제하지 않는다. 다음을 충분히 조사하여 SCody에 가장 적합한 형태를 결정한다.

- Duolingo의 Streak / Personal Record / Achievement / Quest / milestone celebration
- Khan Academy 등의 학습 Progress · Parent Report 사례
- 교육적 gamification 연구

## 2. 핵심 철학

> **공부는 사라지지만, SCody에서는 기록으로 남는다.**

- 학생이 SCody에서 공부할수록 자신의 노력 자체가 하나의 자산처럼 축적되어야 한다.
- 앱을 오래 켜놓거나 의미 없는 클릭으로 기록을 부풀릴 수 있어서는 안 된다.
- 실제 학습 행동을 기준으로 측정해야 한다.
- 학생에게는 '성취감'을, 학부모에게는 '신뢰'를 주는 것이 목표다.

## 3. 학생 경험의 설계 축

학생 경험은 크게 다음 축을 중심으로 설계한다.

- 오늘 얼마나 공부했는지
- 며칠 동안 꾸준히 공부하고 있는지
- 지금까지 얼마나 공부했는지
- 자신의 최고 기록이 무엇인지
- 최근 자신의 기록을 갱신했는지
- 틀린 문제를 얼마나 다시 학습하고 해결했는지
- 이번 주의 내가 지난주의 나보다 어떻게 성장했는지
- 앞으로 어떤 milestone이 가까워지고 있는지

특히 SCody에서는 단순 풀이량뿐 아니라 **오답을 다시 학습하고 해결한 과정 자체를 중요한 성취 기록으로 취급**한다. 틀리는 것을 실패가 아니라 성장 과정으로 느끼게 만들어야 한다.

## 4. 지표 후보

학생이 자연스럽게 다음과 같은 기록을 갖게 될 수 있다.

### 4.1 누적 기록

- 현재 연속 학습일
- 최장 연속 학습일
- 총 학습일
- 누적 실제 학습 시간
- 누적 풀이 문항
- 누적 학습 지문/세트
- 누적 오답 학습 수
- 누적 오답 해결 수

### 4.2 개인 최고 기록

- 하루 최다 학습 시간
- 하루 최다 풀이 문항
- 하루 최다 오답 해결
- 주간 최고 학습 기록

### 4.3 milestone · achievement

- 7일 / 30일 / 50일 / 100일 연속 학습
- 100 / 500 / 1,000 / 5,000문항 풀이
- 10 / 50 / 100 / 500개 오답 해결

**단, 위 목록을 그대로 구현하라는 의미가 아니다.** 먼저 SCody의 실제 학습 구조와 기존 데이터 모델을 분석한 뒤 가장 의미 있는 지표를 선택하고, 필요하면 더 좋은 지표를 새롭게 제안한다.

## 5. Student UX

- 학생 홈에서는 '오늘의 기록'과 현재 연속 학습 상태가 매우 자연스럽게 보여야 한다.
- 학습을 끝냈을 때에는 단순 완료 toast가 아니라, 기록이 실제로 하나 더 쌓였다는 느낌을 강하게 준다.

예:

- "오늘 38문항 · 47분 · 오답 6개 해결"
- "🔥 17일째 공부 중"
- "새로운 기록! 하루 최다 오답 해결 8개 → 11개"
- "30일 연속 학습 달성 — 30일 동안 1,284문항을 풀었습니다."

연출과 디자인:

- 기록 갱신이나 중요한 milestone에서는 적절한 animation / number count-up / celebration / haptic 등의 연출도 적극적으로 검토한다. 다만 유치한 게임 UI가 되지 않게 한다.
- 고등학생이 사용해도 세련되고 자랑스럽게 느껴지는 디자인이어야 한다.

'나의 기록' 영역:

- 별도의 **'나의 기록'** 영역을 두는 것도 적극적으로 검토한다.
- 학생이 지금까지 자신이 쌓아온 공부의 양을 한 화면에서 바라보며 만족감을 느낄 수 있도록 구성한다.

## 6. Streak

- 연속 학습은 핵심 retention 장치로 사용한다.
- 하루 빠졌다고 장기간의 노력이 무가치해지는 구조는 피한다.
- 현재 streak와 longest streak는 별도로 관리한다.
- 필요하다면 주간 목표 달성 등을 통해 얻을 수 있는 제한적인 기록 보호 장치도 설계한다.
- 단순 앱 실행은 학습일로 인정하지 않는다.
- 기존 Scody 구조를 분석해 무엇을 '의미 있는 학습일'로 인정할 것인지 합리적인 규칙을 만든다.

## 7. Self Competition

초기 버전에서는 전체 학생 leaderboard보다 **과거의 나와 경쟁하는 구조**를 우선한다.

예:

- 지난주 187문항 → 이번주 243문항 (+30%)
- 최근 4주 평균보다 +18%
- 최장 연속 기록까지 3일 남음
- 이번 주 최고 기록 갱신

학생이 다른 학생과 비교되어 좌절하기보다 자신의 기록을 깨고 싶도록 만든다.

## 8. Parent UX

- 학부모에게는 학생용 gamification 화면을 그대로 보여주지 않는다.
- 학부모 대시보드에서는 자녀의 학습 노력을 한눈에 이해할 수 있는 **'학습 증명'** 형태로 구성한다.

예를 들어 다음을 사용한다.

- 이번 주 학습 일수
- 실제 학습 시간
- 풀이한 문항
- 완료한 학습량
- 오답 학습 및 해결량
- 목표 달성 일수
- 현재 연속 학습일
- 최근 4주 consistency
- 지난주 대비 변화
- 최근 달성한 기록 및 milestone

요구되는 이해 속도:

> "이번 주 아이가 실제로 얼마나 공부했고, 얼마나 꾸준했으며, 무엇이 개선됐는가"

가 5초 안에 이해되어야 한다.

시각화:

- 최근 7일 / 28일 학습 heatmap, 주간 추이 등 적절한 시각화도 검토한다.

## 9. 데이터 신뢰성

이 시스템에서 매우 중요한 부분이다.

- 단순 화면 체류 시간을 학습 시간으로 기록하지 않는다. 실제 activity가 있는 학습 시간만 계산한다.
- 새로 필요한 데이터 모델이나 aggregation 구조가 있다면 기존 Supabase schema를 먼저 면밀하게 분석한 후 확장한다.
- 가능하면 raw learning event와 daily aggregate의 역할을 구분하여 장기적으로 통계를 확장하기 쉬운 구조를 사용한다.
- 중복 요청, 새로고침, 문제 반복 풀이, 백그라운드 상태, idle 상태 등으로 기록이 비정상적으로 증가하지 않게 한다.
- 기존 사용자에게 이미 남아 있는 학습 데이터로 과거 기록을 일부 복원할 수 있다면 migration / backfill도 검토한다.

## 10. 구현 방식

### 10.1 선행 분석

먼저 코드베이스 전체를 분석하여 현재 SCody의 다음 구조를 정확히 이해한다.

- 학생 홈
- 문제 풀이
- 학습 세션
- 오답노트
- 사용자 프로필
- 학부모 대시보드
- Supabase schema 및 RLS
- analytics / event 관련 구조
- 디자인 시스템

### 10.2 병렬 검토

그다음 다음 관점에서 병렬로 검토하고 최종안을 정리한 뒤 구현한다.

- product / UX 관점
- 교육적 gamification 관점
- 데이터 모델 관점
- frontend / backend 관점

### 10.3 통합 원칙

- 단순 mockup이나 별도 demo page를 만들지 않고 **현재 실제 SCody product flow 안에 완전히 통합**한다.
- 기존 UI/UX와 동떨어진 디자인을 만들지 않는다. 현재 디자인 시스템을 유지한다.
- 다만 기록과 milestone을 확인하는 순간만큼은 SCody에서 가장 만족감 있는 interaction이 되도록 과감하게 개선한다.

### 10.4 구현 산출물

다음을 실제로 구현한다.

- 필요한 DB migration
- types
- hooks / services
- aggregation logic
- UI components
- student pages
- parent dashboard

제약:

- 기존 기능을 깨뜨리지 않는다.
- 모바일 / 태블릿 / 웹 반응형을 모두 고려한다.

# 13. 구현 결과 (2026-08-19 · D-179)

이 절부터는 위 요구사항을 실제로 구현한 결과다. 결정 기록은 마스터 플랜 `D-179`, 진행 기록은
`docs/archive/SCODY_WORKLOG_2026-07.md`의 같은 날짜 항목에 있다.

## 13.1 조사에서 채택한 핵심 설계 원칙

1. **자기 기준 비교만 쓴다.** 전체 학생 leaderboard를 두지 않았다. 숙달 목표 지향(자기 기준)은
   지속에 기여하고 성과 목표 지향(사회 비교)은 하위권 학습자를 이탈시킨다는 것이 교육
   gamification 문헌의 반복된 결과다. 상대는 `지난주의 나` · `최근 4주 평균의 나` · `나의 최고
   기록`뿐이다.
2. **보상이 아니라 정보로 준다.** 포인트·화폐·아바타·레벨을 두지 않았다. 외적 보상은 내재 동기를
   밀어낼 수 있고, 여기서 주려는 것은 `내가 쌓은 것이 보인다`는 사실 자체다.
3. **다음 목표는 가깝고 구체적이어야 한다.** milestone은 달성한 것보다 **다가오는 것**을 먼저
   보여 주고 남은 수를 함께 말한다(근접 목표).
4. **streak은 하루 결석에 무가치해지지 않아야 한다.** Duolingo가 streak freeze로 답한 자리다.
   주간 목표(5일)를 채우면 **기록 보호**가 **2개**(주말 이틀만큼) 생겨 빠진 날을 메운다(보유
   상한 2). 다만 **보호받은 날은 연속을 늘리지 않는다** — 공부하지 않은 날을 `17일째 공부 중`의
   하루로 세면 그 숫자가 거짓이 된다.

   처음에는 하나만 줬는데, 주말은 이틀이라 주 5일을 매주 지키는 학생의 연속이 **일요일에
   끊겼다**(최장 5일 · 첫 milestone `7일 연속` 도달 불가). D-181이 고쳤다.
5. **오답을 다시 풀어 해결한 것이 이 서비스에서 가장 큰 성취다.** 이미 있는 인출 기반 복습
   사다리(D-176)의 끝이 `익힘`이고, milestone의 한 축을 그것으로 뒀다. 오답은 `담은 것 · 다시
   푼 것 · 맞힌 것 · 익힌 것` 네 사실로 갈라 말한다.
6. **측정할 수 없는 것을 기록이라 부르지 않는다.** 화면 체류 시간을 학습 시간으로 쓰지 않고,
   판정은 모두 서버가 한다.

## 13.2 최종적으로 추가한 기능

- **학습일 판정**: 그 날 서버가 채점한 문항 3개 이상(제출한 학습의 문항 + 다시 푼 오답 카드).
  앱 실행은 인정하지 않는다.
- **연속 학습일**: 현재 · 최장을 따로 관리하고, 주간 목표 달성으로 얻는 기록 보호(최대 2개)가
  결석 하루를 메운다. 오늘은 아직 판정하지 않는다(끝나지 않은 하루를 결석으로 세지 않는다).
- **누적**: 총 학습일 · 실제 학습 시간 · 푼 문항 · 완료한 학습 · 담은 오답 · 다시 푼 오답 ·
  다시 풀어 맞힌 오답 · 익힌 오답 · 평균 정답률.
- **개인 최고 기록**: 하루 최다 풀이 · 하루 최다 학습 시간 · 하루 최다 오답 해결 · 주간 최다
  풀이 · 최장 연속 학습(+ 따라잡기까지 남은 일수).
- **기록 갱신 감지**: 오늘(이번 주) 값이 `오늘을 뺀 최고`를 넘으면 새 기록이다.
- **milestone**: 연속 7/30/50/100일 · 문항 100/500/1,000/5,000 · 익힘 5/20/50/100 ·
  학습일 30/100/365. 다가오는 것과 이룬 것을 갈라 보여 준다.
- **과거의 나와 비교**: 이번 주 vs 지난주(문항·시간·일수) · 최근 4주 평균 대비 · 최근 4주 꾸준함.
- **실제 학습 시간 측정**: 활동 기반 누적기 + append-only 시간 원장 + 서버 상한.
- **학부모 학습 증명**: 위 값을 신뢰 관점으로 재구성한 블록과 측정 방식 고지.

## 13.3 학생 경험이 어떻게 바뀌었는지

| 자리 | 전 | 후 |
|---|---|---|
| 홈 | `{이름} 님, 오늘도 반가워요`(정보 없음) | 그 아래 조용한 한 줄 — `17일째 공부 중` + `오늘 38문항 · 47분 · 오답 6개 해결`, 눌러서 기록으로. 강조색을 쓰지 않아 아래 알림 세 줄과 구분되고, 카드가 아니라 히어로와 다투지 않는다 |
| 학습을 끝낸 순간 | 정답률 · 걸린 시간 · 문항별 확인 | 그 아래 **오늘의 기록** 섹션 — 오늘 넘은 milestone 하나와 새로 세운 개인 최고 하나(드문 것을 위에), 숫자가 count-up으로 올라간다. 그리고 오늘 한 공부 · 연속 학습 두 줄 |
| 기록 탭 | 정답률 카드 + 완료한 학습 목록 | `지금까지 42일 공부했어요` 머리글자 → 오늘(연속·기록 보호) → 최근 4주 잔디 → 이번 주(지난주·최근 4주 평균 대비) → 나의 최고 기록 → 지금까지(누적 8줄 + 정답률) → 다가오는 기록 → 이룬 기록 → 완료한 학습(그대로) |
| 걸린 시간 | 화면을 열어 둔 시간 | 활동이 있는 동안만 센 시간. 오답 복습 시간도 함께 쌓인다 |

축하 연출의 경계: 이모지·반짝임·그라데이션·칭찬 문구를 두지 않았다. 강조는 강조색 하나와 큰
숫자, 그리고 count-up 하나다(모션 줄이기에서는 목표값을 즉시 그린다). 축하 블록은 화면에 최대
두 개이고, 대부분의 날에는 나타나지 않는다.

## 13.4 학부모 경험이 어떻게 바뀌었는지

리포트의 AI `이번 주 요약` **바로 아래**에 `이번 주 학습 증명`이 생겼다 — 요약 문장을 읽은
학부모가 곧바로 묻는 것이 `정말 그만큼 했나`이고, 그 답을 달 선택 뒤로 미루면 이번 주 상태를
보려고 달을 골라야 했다.

- 머리 문장 세 값(`5일 · 3시간 20분 · 243문항`)과 주간 목표 달성 여부
- 최근 4주 잔디
- 지표 8줄: 공부한 날 · 실제 학습 시간 · 푼 문항 · 완료한 학습 · 오답 다시 학습(그중 맞힌 수) ·
  익힌 오답 · 연속 학습 · 최근 4주 꾸준함(최근 7일도 함께). **줄마다 지난주 대비**가 붙는다.
- 자녀가 달성한 기록 최대 2개
- **측정 방식 고지 한 줄** — 이 블록에서 가장 중요한 줄이다: 학습 시간은 활동이 있는 시간만
  세고, 화면을 열어 둔 시간이나 다른 앱을 보는 동안은 세지 않고, 문항 수와 정답 여부는 서버가
  채점한 결과라고 밝힌다.

학생용 gamification은 그대로 보여 주지 않는다 — 축하·다가오는 목표·기록 갱신 알림이 없다.
누적은 지표 목록에 넣지 않고 캡션 한 줄로만 말한다(리포트에 누적 총합을 두지 않는 D-050을
깨지 않기 위해서다). 학원에는 어떤 경로도 열지 않았다.

## 13.5 DB/schema의 주요 변화

마이그레이션 4개(`0043`~`0046`). 실측(2026-08-19, live DB): 표 30 · 뷰 8 · 함수 51 · 정책 57.

- **`study_activity`**(새 표): 활동이 있었던 학습 시간 조각. append-only이고 `select` 범위는
  본인·연결된 학부모·운영자다. **학원 경로를 만들지 않았다** — 이 표에는 개인 학습 시간이 출처
  구분 없이 섞여 있어 학원이 읽으면 학생이 집에서 몇 분 공부했는지가 드러난다.
- **`wrong_notes.graduated_on`**(새 컬럼): 익힘에 **처음** 닿은 날. 유지 복습 실패로 익힘에서
  떨어져도 지우지 않는다(지금 상태는 `state`가 말한다). 가드 트리거가 세우고 클라이언트 쓰기를
  막는다. 지난 데이터는 복습 로그의 마지막 정답일로 백필했다.
- **`v_daily_learning_stats`**(새 뷰): 일별 집계 층. `security_invoker = on`이라 밑 표들의 정책이
  범위를 정한다(학원 교직원에게는 0행).
- **`rpc_student_records`** · **`rpc_readable_records`**(새 함수): 화면이 쓰는 묶음. 권한은
  `can_read_student() or is_admin()`이고 대상은 서버가 정한다.
- **`rpc_log_study_time`**(새 함수): 학습 시간을 더하는 유일한 문. 한 번 900초 · 하루 8시간으로
  **깎아서** 넣고 실제로 넣은 초를 돌려준다.
- 트리거: `attempts_time_clamp`(문항당 15분·최소 10분 상한) ·
  `tg_wrong_notes_schedule_guard` 개정(`graduated_on` 보호와 설정).

**집계 표를 만들지 않았다.** 증분 갱신은 `이미 셌는지`를 어딘가에 기억해야 하고 그 기억은
새로고침·재시도·중복 요청에서 갈린다. 뷰는 이미 쌓인 원천을 읽으므로 **기존 사용자의 과거
기록이 첫 조회에서 전부 나오고 옮길 숫자가 없다** — 요구사항 9절의 migration/backfill이
`graduated_on` 하나로 끝난 이유다.

## 13.6 구현하면서 내린 중요한 판단

1. **기록을 저장하지 않고 파생한다**(위 13.5). 중복 집계와 백필이 생길 자리를 만들지 않았다.
2. **`축하했음` 표시를 저장하지 않는다.** `오늘 값 > 오늘을 뺀 최고`와
   `지금 값 - 오늘분 < 기준선 <= 지금 값`은 오늘 안에서 몇 번 계산해도 같은 답이라, 화면을
   두 번 열어도 두 번 세지 않는다.
3. **익힘은 `state`가 아니라 `graduated_on`으로 센다.** `state = 'graduated'`를 세면 유지 복습
   실패에 누적이 **줄어든다** — 기록은 그런 값이 아니다.
4. **같은 날 같은 학습을 다시 낸 것은 한 번만 센다.** 25문항 세트를 앉은 자리에서 40번 내면
   1,000문항이 되는데 그것은 공부가 아니라 버튼이다. **다른 날 다시 푸는 것은 센다** — 분산
   인출이 이 레포 복습 스케줄의 근거다.
5. **학습일 기준을 3문항으로 정했다.** 1이면 카드 한 장(30초)이 `공부한 날`이 되어 학부모
   화면의 `이번 주 5일`이 학습량을 말하지 못하고, 5·10이면 달성 경로가 없는 날이 생긴다(가장
   작은 세트가 3문항 · 오늘 볼 오답 큐는 하루 5장).
6. **기록 보호를 목표를 채우는 순간, 주말 이틀만큼 준다**(0046이 0044를, 0047이 0046을 고쳤다).
   주가 끝날 때 결산하면 `월~금 채우고 토요일 결석`에서 보호가 생기기 전에 끊기고, 하나만 주면
   일요일에 끊긴다 — 둘 다 실측으로 확인했다.
11. **진행 중인 주는 같은 길이의 창과 비교한다**(D-181). `이번 주`(월요일~오늘)를 `지난주`(7일)로
    나누면 월요일 아침에 네 줄이 `-100%`가 된다. 서버가 `lastWeekToDate`를 함께 준다.
    `최근 4주 평균 대비`는 같은 창을 만들 수 없어 비율을 없애고 `평소 한 주`로 바꿨다.
7. **상한은 거부가 아니라 깎기다.** 거부하면 학생이 방금 한 공부가 오류로 보인다.
8. **홈에 큰 숫자를 두지 않았다.** 히어로가 이 화면의 하나뿐인 주요 행동이고(D-167), 위에 면을
   더하면 무엇을 먼저 볼지 갈린다. 축하는 결과 화면과 기록 화면이 맡는다.
9. **잔디를 요일에 맞추지 않았다.** 맞추면 앞줄에 최대 6개의 빈 자리가 생기고 그 빈 자리와
   `공부하지 않은 날`이 같은 모양이 된다 — 세지 못하는 격자가 된다.
10. **`formatDuration` 사본을 만들었다가 지웠고, 구현을 `clock.ts`로 옮겼다.** 같은 이름이 이미
    있었고(D-178), 사본을 두면 같은 4,512초가 화면마다 다른 글자가 된다. 학생 화면 둘의
    `fmtTime`도 함께 옮겨 A-147을 닫았다. 옮긴 이유는 검증 스크립트다 — 원래 자리인
    `learning.ts`는 훅을 담아 react-native을 끌어오고, 그러면 `scripts/verify-records.ts`가 그
    모듈을 지나 학습일 기준 상수를 가져올 수 없다(실측으로 `tsx`가 멈췄다).

## 13.8 이후 확장하면 좋은 기능

마스터 플랜 `남은 작업`에 A-149 · A-150 · A-151로 등록했다.

- **주간 추이선**(A-149): `rpc_student_records`가 최근 8주를 이미 내려보내는데 읽는 화면이 없다.
  `Sparkline`이 레포에 있다.
- **학습 시간 보관 기간**(A-150): append-only 표라 무한히 자란다. 일별로 접는 배치가 가장 단순하다.
- **알림**(M-DEC-6): 차례가 온 오답과 이어질 연속을 앱 밖에서 알릴 채널이 하나도 없다. 이 시스템의
  retention 가치는 `그 날 학생이 온다`는 전제에 걸려 있다.
- **영역별 기록**: 지금 기록은 국어 전체다. 문학·독서·문법을 갈라 보면 `무엇을 많이 했나`가 아니라
  `무엇을 덜 했나`를 말할 수 있다.
- **학부모 주간 요약이 기록을 인용하기**: AI 요약(`weekFacts`)은 아직 달 단위 계산만 받는다.
  연속 학습일과 기록 갱신을 넘기면 요약 문장이 `무엇이 개선됐는가`를 더 정확히 쓴다.
- **친구가 아닌 코호트 비교**: 사회 비교를 피하면서도 `같은 학년의 중위값`처럼 익명 집계와
  비교하는 선택지는 남아 있다. 다만 도입 전에 하위권 학습자에게 미치는 영향을 검토해야 한다.

# 14. 검토와 수정 (2026-08-19 ~ 08-20 · D-180 · D-181)

만든 뒤 `/product-review 학생 기록 흐름`으로 제품·UX 두 관점에서 검토했다. **Critical 1 · High 11
· Medium 12 · Low 6**이 나왔고 그중 두 관점이 같은 문제를 다르게 말한 것이 3건이었다.

## 14.1 만든 사람이 놓친 것 중 중요한 셋

1. **카드 복습 뒤 기록이 갱신되지 않았다**(Critical). `records`를 조회 묶음에 얹으면서 "모든
   쓰기가 재조회를 부른다"고 가정했는데, 재조회를 하는 헬퍼는 `mutate`뿐이고 **복습 경로는 일부러
   그것을 쓰지 않는다**(카드마다 열 번의 왕복을 기다릴 이유가 없다). 그래서 오답 카드를 다섯 장
   풀어도 홈은 `오늘 3문항을 풀면 기록이 시작돼요`로 남았다 — 서버는 그 날을 이미 학습일로
   판정했는데 화면이 방금 한 일을 안 한 것으로 말했다. 기록만 다시 읽는 경로(`refreshRecords`)를
   두어 고쳤다.
2. **지난 결과를 열어도 오늘의 축하가 그려졌다**(High). 기록 탭에서 지난주 결과를 열면
   `다 풀었어요.` 아래에 오늘 세운 기록이 굴러갔다 — 값은 오늘에 대해 참인데 **배치가 인과를
   주장한다.** `attempt.dateISO === todayISO()`로 막았다.
3. **최고 기록이 없는데 날짜를 "세웠어요"라고 말했다**(High). 서버의 `array_agg(… order by 값
   desc, day desc)[1]`은 값이 전부 0이어도 가장 최근 날짜를 준다. 실측: seed 14명 중 **12명**이
   `하루 최다 오답 해결 · 0개 · 8월 17일에 세웠어요` 상태였다. 값이 0인 축은 줄을 만들지 않는다.

- **잔디**: 칸 크기에 상한(48px) — 넓은 화면에서 한 변 93.7px이 되어 화면의 주인공이었다.

- **축하 블록**: 면을 `accentSoft` + `accent` 테두리에서 `surface` + `border`로 — 그 한 벌은 이 앱의
  **`선택됨/켜짐`** 표현이라(고른 선지·켜진 `IconButton`·활성 탭) 누를 수 있는 것처럼 보였다.
- **이름과 단위**: `완료한 학습`이 한 화면에서 세 수를 가리켰다(→ `제출한 학습` 분리) ·
  `지금까지`가 머리글자와 섹션 제목 둘이었다(→ `쌓아 온 기록`) · `다가오는 기록`의 `4 남음`에 단위
  없음 · milestone 축하가 `100문항 풀이`를 `100개`로 셌다 · `8개을 넘었어요`(조사 미계산) ·
  `08월 01일`(형식 미통일).
- **학생에게도 측정 고지**를 뒀다. 학부모에게만 있었는데 행동을 바꿔야 하는 쪽은 학생이다.
- **기록 없는 계정**의 기록 탭이 통째로 비어 있었다 — 홈이 `나의 기록 보기`로 보내는 목적지다.
  이제 규칙 한 줄과 `다가오는 기록` 세 줄이 선다.
- **홈 기록 줄**: 두 줄일 때 `tap.textLine`의 음수 마진이 덩어리 간격을 5px로 먹었다(그 상수는
  캡션 한 줄 전용이다) · 눌린다는 신호가 이 화면에서 가장 흐린 색이었다.

검토가 남긴 다음 개선 후보 다섯을 구현했다(D-182 · 워크로그 2026-08-20 항목).

# 15. 정리 (2026-08-20 · D-183)

만든 뒤 `/simplify`를 재사용·단순화·효율·고도 네 관점으로 돌렸다. 중복 제거 후 **26개**가 나왔고
**27개를 적용**했다(건너뜀 5 · 보류 3 · `그대로 두라` 판정 28).

## 15.1 값이 큰 순서로 셋

1. **뷰가 학생 필터를 원천까지 내려보내지 못했다.** CTE 다섯 개를 각각 두 번 참조해 PG의 인라인
   조건을 깨뜨렸고, 그래서 한 학생의 10행을 얻는 데 원천 94행을 전부 집계했다 — 있는 인덱스
   네 개가 하나도 쓰이지 않았다. 실측 `12.67ms → 0.51ms`(0050).
2. **교체 단위가 300줄이었다.** 규칙을 세 번 고치는 동안 약 860줄이 `바뀌지 않았다`는 사실만
   다시 적힌 SQL이었다. `f_window_sum`·`f_student_streak`로 쪼개 다음 변경을 60줄로 만들었다(0051).
3. **주석에 적어 둔 근거가 거짓이 된 자리 셋.** `말투가 다르다`(문자열이 같았다) ·
   `두 곳에서 가져오지 않게`(아무도 쓰지 않았다) · `읽기는 함수 하나`(둘이었다).

## 15.2 이 시스템이 남긴 교훈

**근거를 적는 관례에는 그 근거가 낡는 실패 모드가 딸려 온다.** 이 레포는 "왜 이렇게 했는가"를
주석에 남기고, 그 덕에 D-179~183의 판단이 전부 되짚을 수 있었다. 그런데 사본과 낭비는 다음
사람이 발견하는 반면 **근거가 적혀 있으면 아무도 의심하지 않는다** — 셋 다 쓴 시점에는 사실이었고
그 뒤 코드가 바뀌면서 거짓이 됐다. 검토를 도구로 돌린 것이 그 셋을 찾은 유일한 이유다.

**추정과 실측의 차이가 두 번 컸다.** 효율 관점은 SQL 항목을 `추정`이라 밝히고 측정 지점까지
알려 줬는데(`verify-records.ts`가 이미 소유자 접속을 열어 두었다), 실제로 재 보니 `seed에서는
무료`로 본 것이 25배였다.

# 16. 이 시스템에 닿은 뒤의 변경 (2026-08-20 · D-184)

로그인·가입을 이메일 기준으로 바꾸면서 **데모 계정 여섯**이 새로 생겼고(학생2·학부모2·학원2),
그 학생 둘에게 이 시스템이 말할 것이 있도록 기록을 심었다.

- **학생1**: 개인 풀이 10건(`-1~-5` 연속 다섯 날 + `-9,-12,-17,-23,-31`) · 노트 5건 ·
  복습 6건. 28일 잔디에 아홉 날이 들어가고 `-31`이 8주 막대의 먼 쪽을 채워 **주간 비교에
  비교할 상대**가 생긴다. 실측 화면: `5일 연속` · `오늘 다시 볼 오답 3개` · 기록 탭 `10일 공부`.
- **학생2**: 개인 풀이 3건 · 노트 2건. 같은 화면이 **적은 데이터**에서 어떻게 보이는지 보는 자리다.

**연속·보호 값은 검증에서 등호로 단정하지 않는다** — 주 경계가 월요일이라 seed를 돌리는 요일에
따라 달라진다. 총계(풀이·노트·복습)만 단정한다.

`db:verify:records` 72/0과 `verify-note-schedule` 86/0은 이 데이터가 들어온 뒤에도 그대로다 —
항등식(`graded = 풀이 + 복습` · `학습일 ⟺ 3문항`)이 새 학생에게도 성립한다는 뜻이다.
